<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser (untrusted input) → Supabase Auth | Email/password submitted from the client cross into the auth service |
| auth-failure response → rendered UI | Error content from Supabase could leak account existence if echoed verbatim |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04 | Information disclosure | login error handling | mitigate | Render a fixed generic toast ("Invalid email or password"); never surface `error.message` — prevents account enumeration (ASVS V2 auth error uniformity) |
| T-01-05 | Tampering / injection | login form input | mitigate | zod `safeParse` validates shape before any call; Supabase parameterizes auth — no string concatenation into queries |
| T-01-06 | Spoofing | credential submission | accept | Brute-force throttling relies on Supabase Auth's built-in rate limiting; no custom lockout in v1 (low-value internal staff portal, admin-seeded accounts) |
| T-01-07 | Repudiation | sign-in events | accept | Auth events are logged by Supabase; app-level audit viewer is deferred (v2) |
</threat_model>
