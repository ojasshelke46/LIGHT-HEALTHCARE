<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Supabase Storage | File bytes cross into the private scan-results bucket; only lab_tech may insert (deployed storage policy) |
| client → orders table | Status/result writes are RLS-scoped; lab_tech role only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04 | Tampering / DoS | File upload (type/size) | mitigate | Client checks `accept="image/*,application/pdf"` + 20MB cap for UX; the authoritative boundary is the deployed scan-results insert policy (lab_tech only) — client checks are not trusted |
| T-03-05 | Tampering | Object key path traversal | mitigate | Filename sanitized `[^a-zA-Z0-9._-]→_` and namespaced under `orders/{orderId}/{timestamp}-` so a crafted filename cannot escape the order's prefix |
| T-03-06 | Information Disclosure | result_url storage | mitigate | Store the Storage PATH, never a public URL; reads go through getResultUrl signed URLs (03-01, T-03-01) |
| T-03-07 | Elevation of Privilege | orders status writes | accept | orders writes require the lab_tech RLS grant (deployed); anon client only, no service-role in browser |
</threat_model>
